# CLAUDE.md: Delhi EV Charger Siting website

This repository is the public website for an Interdisciplinary Major Project at FLAME University:
*A Comparative Analysis of Algorithms to Optimise EV Charging Station Locations in NCT Delhi*. It shows three ways
of siting public charging stations for electric four-wheelers in Delhi: a policy grid rule, weighted K-means and the
Maximal Covering Location Problem (MCLP). All three run on the same demand estimate and are shown side by side.

Live site: <https://shaunakjoshi777.github.io/ev-go-brrr/>. GitHub Pages deploys from `main` (root folder). **Every
push to `main` is live within a minute or two**, so work on a branch and open a pull request. A teammate merges it
after checking the preview.

## The one rule that matters most: results, not a verdict

The team decided that the three methods can't be ranked fairly. Each one optimises a different objective (compliance
with a spacing rule, average distance, coverage within a radius), so any yardstick favours one of them. The site
reports what each method produces and explains why there's no winner.

- **Don't add** winner markers, highlighting of the "best" value, sorting by a metric, scores, rankings, or
  MCDM/TOPSIS results.
- **Don't use** wording such as "best", "better", "outperforms", "superior", "most effective" or "wins" about the
  methods. "Optimal" is fine only in its solver sense ("proven optimal").
- The comparison table in the explorer stays a plain table: no colour coding, bold or icons on individual values,
  and no "not a ranking" caption (the team decided against it).
- Keep the "Why there's no winner" section.

## Accuracy

- Every number on the page comes from the project data or code outputs. `NOTES.md` has a table that says where each
  one comes from. Don't invent, round differently or "update" a figure without a source.
- If a number isn't known, show a visible placeholder: `<span class="tbd">[TBD: what is missing]</span>`, and add it
  to the placeholder list in `NOTES.md`.
- `explorer_data.json` and `site_facts.json` are generated by `build_data.py`. **Don't edit them by hand.** The script
  needs the full project folder (the analysis code and data), which isn't in this repository. Ask Shaunak to re-run it
  if the data has to change.
- `precompute_layouts.py` is the team's original export script, kept for reference. Don't change it.

## What's safe to change, and what isn't

Restyling is welcome: layout, typography, spacing, section design, illustrations, the hero, the method cards.

Leave the behaviour of the explorer alone unless the team agrees. In `assets/explorer.js` these produce the numbers
shown on the page:

- `metrics()`: coverage within the radius, mean distance and farthest cell;
- `consensusSites()` / `nearest()`: a consensus site is a grid station with both a K-means and an MCLP station within
  1 km;
- `nearestBudget()` and the "Same number of stations as the grid" link;
- the controls themselves: radius 1.5 / 2.1 / 3 km, the link toggle, coverage rings, existing 4W chargers, consensus
  sites, and the three sliders (grid cell size, K-means *k*, MCLP *p*).

Drawing code (colours, marker sizes, line weights) can change, as long as the maps stay readable in both themes.

## Design constraints

- **Method colours, used everywhere:** grid `#2f62c9`, K-means `#d9771f`, MCLP `#23946b`, existing chargers
  `#c2255c`. Dark-mode variants are in `assets/site.css`. Demand is a grey ramp. Don't reuse these colours for
  unrelated decoration.
- **Dark mode must keep working:** both `prefers-color-scheme` and the toggle button (`data-theme` on `<html>`). Canvas
  colours are read from the CSS custom properties, so add new colours as tokens in both themes.
- **Responsive down to phone width (375 px)**, with no sideways page scroll. The three map plates stack on phones.
- **Accessibility:** keyboard-usable controls, visible focus, `role="img"` + `aria-label` on each canvas, and the text
  summary under each map (`sum-grid`, `sum-kmeans`, `sum-mclp`, `sum-demand`). Respect `prefers-reduced-motion`.

## Technical constraints

- A static site: plain HTML, CSS and JavaScript, no build step, no backend, no API keys. Agree with the team before
  adding a framework or bundler, because it changes how the site deploys.
- External scripts and styles load from CDNs pinned to an exact version (KaTeX 0.16.11 on jsDelivr, IBM Plex from
  Google Fonts). Keep a system-font fallback. Don't add analytics or trackers.
- Keep the OpenStreetMap attribution in the Data section (ODbL requires it).

## Checking a change

Preview locally from the repository root:

```bash
python3 -m http.server 8000
```

Then open <http://localhost:8000> (opening `index.html` from disk won't work, because the page fetches
`explorer_data.json`). Before opening a pull request, check:

- every explorer control still works, and the table and the stats under each map update;
- light and dark themes;
- desktop and phone widths;
- no errors in the browser console;
- a search for evaluative words (the list above) finds nothing new.

Record any change to content, wording about the methods, or assumptions in `NOTES.md`.
